# SIGIL parity goldens

Generated by `node scripts/golden.mjs` from the **real** TypeScript DSP under
`src/dsp/`. Do not hand-edit anything in this directory, and do not edit the
TypeScript to make a golden match — the TypeScript is the reference.

Regenerate whenever `src/dsp/**` changes:

```
node scripts/golden.mjs           # write goldens
node scripts/golden.mjs --check   # write, then regenerate into a temp dir and diff
```

`--check` is the determinism gate. It must print
`determinism OK: N files byte-identical across two runs`.

## Files

| file | what |
|---|---|
| `manifest.json` | full description of every case: module, tolerance, params, sha256 |
| `index.tsv` | the same case list, tab-separated, for `parity.cpp` |
| `params.tsv` | `caseId \t key \t value`, the flattened `params` of every case |
| `<id>.f32` | the golden output: raw little-endian float32, interleaved |
| `<id>.in.f32` | the input signal for that case, same format |
| `<name>.f32` (assets) | shared material, e.g. the sampler's injected buffer |

Everything is 48 000 Hz. Multi-channel data is **interleaved** (L,R,L,R…).

**The input file is literally what the reference passed to `process()`.** It is
never pre- or post-scaled by anything the runner has to know about. Read it and
feed it straight in. (An earlier draft of this harness had one case that
disagreed with itself about this, and it showed up as a 0.735 max error — the
rig caught it, which is the point, but the rule exists so nobody has to.)

## Tolerances, and why

The goldens are float32. One ulp of float32 near unity is 2⁻²⁴ ≈ 5.96e-8, so any
tolerance tighter than about 1e-7 is meaningless for signals near full scale —
the storage format cannot express a smaller disagreement.

| class | maxAbs | rms | applies to |
|---|---|---|---|
| `exact` | **0** | 0 | no transcendental anywhere in the case |
| `coeff` | 1e-6 | 1e-7 | `exp`/`tan`/`pow` at **parameter** rate only |
| `trans` | 1e-5 | 1e-6 | a transcendental **per sample** |
| `chain` | 1e-5 | 1e-6 | full voices and effect chains |

**`exact` means exact.** Pure `+ - * /` and integer ops on IEEE-754 doubles,
evaluated in the same order, produce the same bits on any conforming
implementation. If a `blep` or a `Line` case is off by anything at all, the port
has a real structural difference — a reassociation, a `float` where the
reference has a `double`, or FMA contraction. It is not "floating point noise".

**`coeff` (1e-6)** exists because V8 and Apple's libm do not agree in the last
bit on `Math.exp`, `Math.tan` and `Math.pow`. This is real and already measured
here: `fxcore_onepole_table` shows a **maxAbs of 5.96e-8** — one float32 ulp —
purely from `std::exp` vs V8's `exp`. That is the whole disagreement, on a bare
coefficient table with nothing amplifying it. A recursive filter multiplies that
by roughly `1/(1-|pole|)`, which for anything short of self-oscillation is a
factor of tens, not thousands. 1e-6 leaves ~17 float32 ulps of headroom.

*Note the asymmetry this creates, and it is deliberate: a coefficient that is
wrong in the third decimal produces errors of order 1e-3 to 1e-2. Measured — a
0.1 % perturbation of the ladder's cutoff coefficient produced a maxAbs of
8.8e-4, which is **350× the tolerance**. There is no overlap between "libm
disagrees in the last bit" and "the coefficient is wrong". If a `coeff` case
fails, something is actually wrong.*

**`trans` / `chain` (1e-5)** allow for a per-sample transcendental difference
plus one more hazard: these modules are full of comparison thresholds
(`if (value >= 1)` in the envelope, `if (acc >= 1)` in the bitcrusher, the
stutter's latch). A 1-ulp difference can decide such a branch and shift a state
transition by one sample, which is a large error on exactly one sample.

That is why `parity.cpp` reports the **shape** of a failure:

- `shape: isolated (N samples over tolerance)` → look for a state transition
  landing one sample early or late. Not a coefficient.
- `shape: broad (N% over tolerance)` → a coefficient or a structural difference.

## If you cannot make a case match

Say so, with the measured maxAbs, rms, worst index, and the shape. Do not raise
a tolerance in `harness.mjs`. If you need to demonstrate how close you are, run

```
./build/sigil_parity --case <prefix> --tolerance-scale 10
```

which prints a loud `!! tolerances scaled by 10 - this run is NOT at the stated
bar` so a scaled run can never be mistaken for a passing one.

## Cases that are intentionally silent

`voice_fm_min_a4`, `voice_physical_min_a4`, `voice_sampler_min_a4` and
`voice_sampler_mid_a4` are all zeros: at those parameter extremes the engine
correctly produces nothing (sustain 0, level 0, or a sample window that
collapses and terminates). They are still real tests — a port that makes sound
there is wrong — but note that `parity.cpp` deliberately fails any case where
the candidate is all zeros and the golden is not, so a stub returning silence
can never read as a pass.
